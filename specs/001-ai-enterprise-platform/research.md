# Phase 0 Research - AI驱动企业管理平台核心能力

## 1) 轻量化存储与缓存策略

### Decision
业务主存储使用 SQLite；缓存优先使用进程内 TTL Cache，跨进程一致性场景补充 SQLite 轻量状态表；避免引入额外重型中间件。

### Rationale
- 满足“本地仅 Python + Vue 可运行”的约束。
- 降低部署复杂度，便于快速验证 AI 业务闭环。
- 通过幂等键、事务和锁机制，仍可覆盖核心并发一致性需求。

### Alternatives considered
- PostgreSQL + Redis：并发与扩展性更强，但安装与运维成本高，不符合当前轻量化目标。
- 纯文件存储：实现最简，但事务一致性与查询能力不足。

---

## 2) AI 对话编排方式

### Decision
采用“意图识别 + 工具路由 + 参数补齐状态机”的编排方式，核心对话流程由 `ConversationOrchestrator` 驱动，业务操作通过 Tool 适配器执行。

### Rationale
- 可稳定支持“请假/报销/流程发起/数据查询”等多类动作。
- 参数不完整时可按状态机追问，降低误操作率。
- Tool 层隔离业务服务，便于测试与灰度替换。

### Alternatives considered
- 单提示词直接生成业务结果：实现快，但可控性与审计可追溯性不足。
- 完全规则引擎：稳定但表达能力弱，难覆盖自然语言变化。

---

## 3) NL2SQL 安全策略（改为 NL2Query）

### Decision
首期将“自然语言转查询”收敛为“语义查询 DSL（NL2Query）-> 查询执行器”，默认不直接执行任意生成 SQL；仅对受控白名单查询模板进行参数化执行。

### Rationale
- 在轻量数据库场景下，避免 SQL 注入与越权风险。
- 可将数据权限校验放在 DSL 执行阶段统一处理。
- 后续仍可扩展为多数据库 SQL 适配层。

### Alternatives considered
- 直接 NL2SQL：灵活性高，但安全边界和可解释性成本更高。
- 固定报表查询：安全但不够智能，用户体验受限。

---

## 4) 并发控制模型

### Decision
采用“幂等键 + 乐观锁版本号 + 关键段互斥锁”的组合方案；审批与申请写操作必须携带幂等键，状态变更使用版本号冲突检测。

### Rationale
- 避免重复提交、重复审批、消息重复投递。
- 兼顾实现复杂度与可验证性。
- 满足高并发场景下一致性要求。

### Alternatives considered
- 全局串行队列：一致性强，但吞吐低、延迟高。
- 仅数据库事务：无法覆盖跨请求幂等和重复提交问题。

---

## 5) 日志与审计规范

### Decision
系统日志统一格式：`类名.方法名 >>> 日志信息`，并补充 `trace_id`、`operator_id`、`biz_id` 等结构化字段。

### Rationale
- 对齐项目明确要求。
- 便于排障、审计与链路追踪。
- 可直接用于后续告警和报表分析。

### Alternatives considered
- 仅文本日志：简单但机器分析能力弱。
- 全量 APM 方案：能力强但超出当前轻量化目标。

---

## 6) 设计模式选型（面向本特性）

### Decision
- **Strategy 模式**：按意图类型切换不同业务处理策略（请假、报销、查询等）。
- **Factory 模式**：统一创建 Tool 执行器与查询执行器实例。
- **Adapter 模式**：对接大模型、检索器、通知通道时统一接口。
- **Template Method 模式**：审批流与操作执行流程复用统一步骤骨架。

### Rationale
- 降低模块耦合，保证可替换性与可测试性。
- 适配“轻量落地 + 后续扩展”的演进路径。

### Alternatives considered
- 过程式实现：开发快，但后续维护成本高。
- 过度 DDD 分层：规范高，但首期实现成本偏大。
